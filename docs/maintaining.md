# Maintaining this

Notes for whoever looks after the code — human or agent.

## What it is

Volunteers at the St. Vincent de Paul conference at Nativity Catholic Church in Menlo Park deliver
food and grocery gift cards to families in need. Requests arrive through a county office and are
recorded in **ServWare** (servware.org), which has no public API. Twice a week volunteers call the
families who have waited longest, pack food, allocate gift cards by household size, drive the
deliveries, and then have to record all of it.

That last step is what this replaces. It used to mean hand-editing spreadsheets and running
terminal commands. It is now a conversation in Claude Desktop.

A second job grew out of the first: occasional projects — Christmas Adopt-a-Family and the like —
need to *understand* the neighbour population, so the tool also pulls slices of it into CSVs.

Another conference could use this, but the assistance type IDs are conference-specific. See
[Another conference](#another-conference).

## How it is put together

One Rust crate, two front ends, and guidance shipped alongside.

```
src/servware/    protocol: login, DataTables endpoints, HTML form extraction
src/domain/      policy, delivery sessions, CSV export, recency
src/main.rs      the `svdp` CLI               — for whoever maintains this
src/bin/mcp.rs   a stdio MCP server           — for volunteers, via Claude Desktop
skills/          conversational guidance      — installed separately
```

**The CLI does not drive the MCP server, and neither drives the other.** They are siblings over
one logic layer, which is why a protocol fix lands in both at once and why the export path could
be debugged through the CLI with confidence it was the same code the extension runs.

Two things are load-bearing and easy to break:

- **`src/servware/form.rs`** extracts *every* named control from a form and applies a checked
  overlay. Never enumerate fields by hand. The live request form has 50 controls; a hand-written
  builder once sent 39 and silently cleared the other 11 on every write.
- **Writes are never trusted on HTTP status.** Spring re-renders a rejected form as 200, so every
  write is confirmed by reading it back.

`CLAUDE.md` has the fuller version of this, including the rules that matter when editing.

## Build and run

```bash
cargo test                  # whole suite, no network needed
cargo clippy --all-targets  # CI runs this with -D warnings

./scripts/build-release.sh  # -> dist/svdp-servware<suffix>.zip, the file volunteers get
./scripts/build-mcpb.sh     # just the extension
./scripts/build-skills.sh   # just the skill zips
./scripts/make-shortcut.sh  # desktop icons that open Claude with the request ready
python3 scripts/gen-fixtures.py   # regenerate synthetic test fixtures
```

Credentials come from `SERVWARE_USER` and `SERVWARE_PASS`, in the environment or a `.env` file.

## What a volunteer receives

One archive per platform:

```
svdp-servware<suffix>.zip
└── svdp-servware/
    ├── START-HERE.txt              the whole setup, inside the archive
    ├── svdp-servware.mcpb          install under Settings → Extensions
    └── skills/
        ├── pulling-svdp-data.zip        add each as a skill, still zipped
        └── recording-svdp-deliveries.zip
```

One unzip, then two kinds of install. The shape is forced by two facts: the MCPB manifest has **no
`skills` field**, so skills cannot live inside the `.mcpb`; and Claude Desktop's skill upload takes
a **zip**, not a folder, so they stay zipped inside the archive.

`START-HERE.txt` is generated by `build-release.sh` and is the **primary** setup document — not
this file, and not the release notes. Volunteers are assumed to read nothing outside what they
were handed.

## Releasing

Push a `v*` tag. Two jobs build two archives: **one universal Mac build** (arm64 and x86_64 joined
with `lipo`, so there is a single Mac download and volunteers never have to identify their
processor) and one x86_64 Linux build.

`workflow_dispatch` is enabled, so the release workflow can be exercised without cutting a tag.
Use it — the first tag push should not be the first time the release path runs.

**Do not hand-build for volunteers.** Let CI do it, so what they install is reproducible.

There is deliberately no Intel Mac runner: GitHub retired `macos-13` in December 2025 (a job
requesting it queues forever) and drops x86_64 macOS entirely after August 2027. Cross-compiling
both slices on an arm64 runner outlives both dates.

`build-mcpb.sh` asserts via `lipo -archs` that both slices are present, and CI re-checks it on the
bundle inside the shipped archive. A bundle silently carrying one architecture would install
cleanly and then fail for half the conference.

## Deploying to a Mac for testing

```bash
./scripts/deploy-mac.sh [host] [remote-path]
```

Syncs, builds a universal archive on the Mac, and drops it on the Desktop — falling back to
`~/svdp-install` when macOS privacy protection blocks SSH from `~/Desktop`, which happens after a
reboot until sshd is granted Full Disk Access.

Two guards exist because both of these went wrong once: the rsync excludes are **anchored**
(`/servware/`, not `servware/`, which also matches `src/servware/` and once shipped a source tree
missing the protocol layer), and the destination is cleared before copying, so a stale artifact
cannot sit next to a fresh one.

## The CLI

Same logic layer as the extension. This is how you debug without going through a chat client.

```bash
svdp health                     # sign-in, request list, and form check
svdp requests                   # open requests with suggested gift card amounts
svdp volunteers                 # volunteer names and ids
svdp request <id>               # one request and what is logged against it
svdp form <id>                  # the edit form, to see what a write would send
svdp snapshot                   # save one page locally, to work offline
svdp snapshot --path /app/...   # capture any page, for protocol spikes
```

`requests` and `volunteers` shorten names to "Ada L." by default; pass `--full-names` when you
genuinely need them. This output lands in terminals, scrollback and agent transcripts.

`snapshot` asks `git check-ignore` about its destination and **refuses to write** if git does not
ignore it. `--out` is relative to your working directory while `.gitignore` anchors `/recordings/`
at the repository root, so the two disagree more often than you would expect.

Data pulls, which write CSVs to the Desktop unless you pass `--out`:

```bash
svdp export-neighbors
svdp export-requests --from 06/01/2026 --to 08/31/2026
svdp export-household-members --from 06/01/2026 --to 08/31/2026
svdp exports                    # what has already been written
```

Writes are dry-run unless you pass `--yes`:

```bash
svdp add-item --request <id> --slot food --dollars 70 --session TEST
svdp complete --request <id> --volunteer <member-id>
```

## Working against production

ServWare is a live county system holding real case records, and every request is attributable to
whoever's credentials are in use. Treat access as a loan.

- **Have a reason for each call.** Do not poll, do not re-run a command to re-read output you
  already have. `svdp snapshot` exists so iteration costs one request rather than one per rebuild.
- **Watch for calls that fan out.** Paginated endpoints turn one command into dozens. The household
  members pull is one page *per household*; it is paced, capped at 200 with a hard ceiling of 400,
  and refuses rather than truncating.
- **Writes are categorically different from reads.** ServWare has no way to delete an assistance
  item once added. Confirm before writing, keep a first write to a single record, and verify by
  reading back rather than trusting a status code.
- **Never print neighbour or volunteer data** into a transcript, a log, or a terminal. Inspect real
  captures by structure — keys, field names, counts — not by dumping values.

## PII

This repository is public and the data concerns families receiving assistance.

- **Never commit CSVs, HAR captures, or anything derived from a real ServWare response.**
  `.gitignore` matches by glob, and CI fails if a real-data file is tracked.
- **Test fixtures are synthetic by construction** (`scripts/gen-fixtures.py`), not scrubbed from
  real data. Field *names* are protocol facts and safe; every *value* is invented.
- **Export columns are an allowlist pinned by a test.** No SSN, no driver's licence, no case notes,
  and no dates of birth — exports carry ages instead, so a spreadsheet passed between volunteers
  never holds name + address + DOB. Every header is asserted as an exact literal: a length check
  cannot catch a *replaced* column, and for a while the assistance table was not checked at all.
- **CSV cells that look like formulas are quoted.** These files get opened in Excel, and ServWare's
  free-text fields are typed by caseworkers.
- **CI's fixture check is by provenance.** It re-runs `scripts/gen-fixtures.py` and fails if the
  tree differs, so a real capture cannot be committed as a fixture. Regenerate whenever you change
  that script, or CI will fail on a diff you did not mean to make.
- Real captures are validated by an **opt-in local test** that reads a path from
  `SVDP_LOCAL_DETAIL_HTML` and prints structure only:

  ```bash
  SVDP_LOCAL_DETAIL_HTML=/path/detail.html cargo test --test local_capture -- --ignored --nocapture
  ```

## Another conference

Assistance type IDs differ per conference. `conference.toml` is compiled into the binary as the
default; override it with a `conference.toml` in the working directory or
`SVDP_CONFERENCE_CONFIG=/path`. The gift-card ladder, the food amount, the visit notes and the
once-a-month delivery interval all live there too.

## Known gaps

Honest list, current as of the last change:

- **The delivery chain has never run end to end through MCP.** `update_session_plan → confirm_plan
  → submit_session` compiles and exposes correctly, and one live write has been verified — but
  through the CLI. This is the half that spends money.
- **CI had never run** until September 2026: `on: push: branches:` listed `claude-rewrite` while
  the working branch was `feature/claude-rewrite`, so nothing matched. Now `['**']`. Its steps have
  been executed locally and pass; no tag has been pushed and no release run has happened.
- **The universal Mac build's x86_64 slice has never been compiled.** The risk sits with
  `aws-lc-rs`, which builds C and assembly; macOS x86_64 is a first-class target for it, so this is
  expected to work rather than known to.
- **Session-expiry re-auth has never been exercised over a real hour-long gap.** ServWare times out
  after 3600s and a long delivery night will cross that.
- **`export_requests` with no date range** auto-approves a walk of the whole history — bounded and
  paced, but the one fan-out not behind an approval dialog.
- **Skill distribution does not scale.** A zip per volunteer is fine for a handful of people and
  nothing more.
- **`WriteUnverifiable` has never fired in practice.** It is the path taken when a write may have
  landed but cannot be confirmed, and it tells the volunteer not to retry. The logic is tested; the
  situation has not occurred.

## Where the reasoning lives

`DECISIONS.md` is the trail of intent: why this is shaped as it is, **including the alternatives
that were rejected and why they lost**. Read it before proposing an architectural change — most of
the obvious-looking alternatives are in there already, ruled out for reasons that are not obvious.
It also records empirical findings, several of which contradict documentation or intuition.

Append to it as part of the work, not as a cleanup pass afterwards.

`api.md` is the reverse-engineered ServWare reference. Where it and a capture disagree, the capture
wins and `api.md` should be corrected.

## About ServWare

There is no official ServWare API; this was reverse-engineered from browser traffic. ServWare is a
good tool and its maintainers deserve the credit for it.

If you work on ServWare and want to talk, please reach out — there is no commercial interest here.
If you are at another SVdP conference with similar needs, likewise. It would be good if this were
useful beyond one parish.
